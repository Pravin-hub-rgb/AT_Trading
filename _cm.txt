make pivot_rule explicit so the C16 rule reaches both halves of v18 and v19

_commit_rule _collect_signals is called four times per v19 run: three HTF windows
via simulate_btc_trades_v7 and one LTF collection. The route selected the origin
rule by rebinding btc_engine._collect_signals. v19_champion.py:255 imports inside
the function body and so saw the rebind; v7_timecap.py:5 imports at module level
and so never did, freezing on whatever _collect_signals was when btc_routes.py:41
first imported it. The v19_champion book therefore ran leg on HTF and origin on
LTF for every request, and returned 499 / +242.28R net while its label claimed
500 / +325.78R.

The same rebinding also meant the default flip in 203e207, which set
pivot_rule="leg" in btc_engine.py, silently moved twenty call sites in eleven
engine files from origin to leg without any caller asking. exp_v19_causal.py now
fails its own pin assert as a result: its retro arm returns 499 / +239.12R, not
500 / +325.78R.

Fix: pivot_rule is a real parameter on simulate_btc_trades_v7 and on both
simulate_htf_ltf_streak_halt entry points, forwarded to all four call sites.
btc_routes.py passes pivot_rule="origin" as an ordinary argument and the
monkeypatch is deleted, which also removes a genuine race: FastAPI serves sync
endpoints from a threadpool and two concurrent requests shared one module global.

The default stays "leg". Flipping it back to "origin" for backward compatibility
would silently return twenty engines to the lookahead pivot.

Measured after the fix, harness, exp_v19_matrix.py:

  leg / leg            n=499  gross +355.72R  net +239.12R
  leg / leg + causal   n=499  gross +355.72R  net +239.12R   causal flag inert

  C16 cost origin to leg: -86.67R over -1 trade

The origin arm reproducing n 500 / net 325.78R confirms the registry pin for
champion_multi_sw10 was correct, and that the earlier "-3.16R" figure came from
the half-applied hybrid rather than from the rule.
