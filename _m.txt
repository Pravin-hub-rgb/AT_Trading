The frontend was never running v19. exp_why_842.py shows the backend data path is correct.

The stats panel read 842 trades, +70R, SL 614, TARGET 228, TRAIL 0. The
decisive clue is TARGET: v19 only ever emits sl, trail or open. A target exit
is the generic simulate_btc_trades path, which is what runs for v1. So the version
state was v1, not v19_champion, and the number was never going to match.
TRAIL 0 followed from the same cause - the v1 engine has no swing-trail ratchet,
and the trail is what turns a 1R stop-out into a +27R runner.
This was never the min_bars fix failing. That fix was necessary but not the cause.

Cause: version was initialised to the literal "v1", and the mount effect only
overrode it when localStorage held a saved book. With no saved book the page ran
v1 on 5m BTCUSDT at the API default minBars=14 - a combination that exists
nowhere in books.ts.
Fixed by making the Book dropdown the origin of the initial state instead of a
value that gets overwritten later:
  tf, symbol, version, htfLtf, htfLtfVer and book all initialise from DEFAULT_BOOK
  the mount effect applies DEFAULT_BOOK when nothing is saved, including
    bookSizing, which previously kept minBars at 14
  the five duplicate declarations that this created are removed
exp_why_842.py added, which proves the backend side is sound:
  15m min_bars=50: backend 2900 swings, harness 2900, identical dirs and keys
  1h  min_bars=10: backend 1601 swings, harness 1601, identical
  trail events: 2900 both, 1601 both
  signals: 2307 both
  engine on harness swings: n=500 net=+325.78R {sl:187, trail:313}
  engine on backend swings: n=500 net=+325.78R {sl:187, trail:313}
The two swing builders are interchangeable. Nothing to fix on the backend.
