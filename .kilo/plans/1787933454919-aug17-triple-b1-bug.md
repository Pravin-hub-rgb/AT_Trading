# Plan: Investigate Aug 17 2026 triple-B1 bug

## Problem
User reports on chart for 2026-08-17:
- Three B1 marks visible
- One at 10:14 (correct — first real break)
- Extra ones at 10:16 and 10:17 (duplicates)

The first-swing engine is supposed to emit exactly ONE B1 per swing (the
"first A/B break → lock" event). Multiple B1s in the same swing indicate
`lock()` is being called more than once for what should be a single locked
direction.

## Relevant code
- `frontend/src/lib/firstswing.ts:320-386` — `step()` decides lock/flip/confirm
- `frontend/src/lib/firstswing.ts:388-412` — `lock()` pushes B1 mark
- `frontend/src/lib/firstswing.ts:432-453` — `flip()` pushes FLIP mark
- `frontend/src/lib/firstswing.ts:414-430` — `confirmDirection()` pushes B2 mark
- `frontend/src/app/chart/page.tsx:318-328` — wires `fsBreaks` from `computeFsV2Results`
- `frontend/src/components/StockChart.tsx:874-887` — renders B1/B2/FLIP as `arrowUp` markers

## Root-cause hypothesis
Look at `step()` lines 347-385 (LOCKED-but-not-yet-confirmed branch):

```
} else if (upBreak) {
  this.lock("up");   // <-- fires EVERY time upBreak while locked-down
} else if (downBreak) {
  this.lock("down"); // <-- same on the other side
}
```

The current code treats every same-side downBreak as a continuation (B2
candidate) and EVERY opposite-side break as a fresh `lock()` — which
emits another B1. So if the engine is in `state="locked"`, `dir="down"`,
and the next bar prints `upBreak && !downBreak` (a clean opposite break),
`lock("up")` is called and a second B1 ("up") is pushed.

In the Aug-17 case the day likely contains:
- 10:14: first B1 (down) — candle extends the morning low
- 10:15-10:16: a small up-wick that pokes the running eHiPivot
  without a real trend reversal
- 10:17: another push the other way

Result: the engine keeps re-locking, pushing B1 each time, until enough
bars later a B2 finally fires and the swing declares.

## Fix design (for the implementing agent)

The cleanest fix is to forbid `lock()` from firing while already
`state === "locked"`. A re-lock on a different side is by definition a
**flip**, not a fresh lock, and should emit a FLIP mark (or merge into
the existing swing). Concretely:

- In `step()` LOCKED branch, replace the two `this.lock("up"/"down")`
  calls with a `this.flip("up"/"down")`.
- `flip()` already pushes a FLIP mark and resets `baseDir`/`b1BarIdx`/
  `cornerPivot` — semantically the right thing here.
- Verify `flip()` does NOT also fire a B1; it only pushes FLIP
  (`firstswing.ts:446-452`). Good.
- Add a regression test that replays 2026-08-17 1-min and asserts
  exactly **one** B1, exactly **one** B2 (or one FLIP), in the right
  order.

Edge case: if a real "reversal" needs a B1+B2 cycle from the NEW
direction, `flip()` already sets `dirConfirmed = true` and `b1BarIdx = -1`
so the engine can immediately start a fresh swing from the counter-
extreme with the next break firing as a new B1 there. This matches the
theory doc.
